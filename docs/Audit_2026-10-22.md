## 2. Executor model (three disjoint order processes)

The safety model is invariant across the entire build. Every order executor:

* has a **disjoint** whitelist (no two bots can trade the same pair);
* runs the same inherited `PaperAutonomous.confirm_trade_entry` veto (verbatim);
* contributes to a **single global** portfolio cap via the read-only
  cross-executor `open_exposure.json` ledger, and fails-closed when the ledger is
  stale or missing;
* **PAPER only** — `authorization.live_trading = NOT APPROVED`, `hard_prohibitions`
  unchanged.

| Executor | Timeframe | Strategy | Pairs | Stake | max_open |
|----------|-----------|----------|-------|-------|----------|
| daily    | 1d        | PaperAutonomous (BTC baseline) → BtcZScore | BTC/USD | $15 | 1 |
| fast     | 5m        | MomentumAlt → FamilyDispatcher → families.py | ETH/XRP/DOT/LINK/SOL/UNI/USD | $10 ea | 2 |
| swing   | 1h        | SwingAlt → FamilyDispatcher → families.py (cost-aware -6% stop) | LTC/AVAX/DOGE/USD | $10 ea | 1 |

Structural: sum of per-pair caps = BTC 15 + 6×10 + 3×10 = **$105**. Fixed policy cap
raised to $105 so `validate_executors` passes the worst case; runtime `min(105,
40% × equity)` still binds to **$40** on the $100 paper account, so breadth of pairs
adds learning surface, not more simultaneous dollars at risk.

## 5. Learning layer (Phase D)

Two consumers of a durable `trade_journal` table (`app/ledger/unbound.db`, schema
in `obs_lib.SCHEMA`):

* `app/learn/perf.py` — pure, deterministic rolling metrics per `(pair, family)`:
  `n`, `win_rate`, `avg_R`, `expectancy_R`, `profit_factor`, `realized_pnl`. Every
  value is `None` at `n=0` (fail-closed; never a fabricated 0).
* `app/learn/journal.py` — upserts one row per CLOSED `paper_trades` row with
  family (from the registry) and `R-multiple = profit_abs / (stake × stop_frac)`.
  `R` is `None` when the risk cannot be computed, again fail-closed.

Fed by `app/scripts/learner.py` (read-only, idempotent, watch mode supported).
Writes two state files the trading path consults:

### 5.1 Strategy gate — auto-demote, NEVER auto-promote

`app/state/strategy_gate.json` is append-only. When a `(pair, family)` group has
`n >= N_MIN = 20` AND `expectancy_R <= 0`, the learner adds a demotion entry.
`policy.is_tradeable(pair)` returns `False` when the pair appears in the file,
so `confirm_trade_entry` rejects the entry and logs a rejection. The gate cannot
flap because **promotion requires a fresh backtest + owner edit of the file**
(there is no code path that removes an entry automatically).

`crypto_status_monitor.notify_demotions` pushes each new gate entry to Telegram
via the `⛔ STRATEGY GATE — AUTO-DEMOTED` format, with a watermark so the file's
history never spams the operator across restarts.

### 5.2 Evidence-scaled sizing

`policy.stake_for_pair(pair, proposed)`:

```
base    = min(proposed, max_stake_usd(pair), loss_cap / stop_distance)
m       = clamp(1.0 + 0.5 · avg_R, 1.0, MAX_EVIDENCE_SCALE=2.0)   # only if n >= 20
stake   = min(base · m, max_stake_usd(pair) · MAX_EVIDENCE_SCALE)
```

**Inert at `m=1.0`.** On a fresh / young account (no `perf.json` or `n<20`) the
result is byte-for-byte identical to the pre-Phase-D formula, so the existing
BTC=15 / alts=10 test assertions still pass without edits. `MAX_EVIDENCE_SCALE=2.0`
is enforced in two places (perf.py + policy.py) so a corrupt `perf.json` cannot
raise a stake beyond 2× the approved per-pair cap.

Per-position 20 % equity ceiling lives in `PaperAutonomous.confirm_trade_entry`
(new step **6b**), after the fresh-equity check and before the exposure check, so
it uses the same equity snapshot that gates the portfolio cap. This means the
evidence multiplier cannot silently bypass the plan's §3 "≤ 20 % equity per
position" rule.

## 6. Supervisor (Phase F — continuous independent operation)

`app/scripts/supervise.py` runs the monitor, the learner, and the order executors
as **detached child process groups**. Restart policy:

* **Never** relaunches an order executor while `policy.is_blocked()` is True. Sends
  a throttled Telegram alert instead (one per 5 min) so a crash-loop cannot spam
  the operator, and so the fail-closed breaker is never bypassed.
* Always keeps the monitor + learner alive even during a breaker trip — the
  operator still needs state visibility and the ledger needs its updates.
* Backoff `5 → 10 → 30 → 60 s (capped)`. A stable 5-minute run resets the ladder.
* SIGINT / SIGTERM handlers on the supervisor drain children cleanly via
  `CTRL_BREAK_EVENT` on Windows (so Python's `KeyboardInterrupt` shutdown path
  runs inside the bot) and `SIGTERM` on POSIX.

### 11.1 Real defect found and fixed — swing 1h OHLCV refresh was stuck

**Status: FIXED 2026-10-22** (see "Root cause" and "Fix" below).

Every ~20 s the swing executor was logging:

```
WARNING - Outdated history for pair LTC/USD.   Last tick is 45508 minutes old
WARNING - Outdated history for pair AVAX/USD.  Last tick is 46288 minutes old
WARNING - Outdated history for pair DOGE/USD.  Last tick is 44728 minutes old
```

The age increased at real-time rate, meaning the newest-known 1h candle for
each of these three pairs was **frozen at ~2026-09-21** and the executor was
not fetching fresh 1h bars. **The fast (5m) and daily (1d) executors did not
emit this warning** — the general Alpaca data path worked, only the 1h path
was broken.

Consequence: **SwingAlt could not evaluate fresh bars, so it could not fire
an entry.** The three swing pairs (LTC/AVAX/DOGE) were effectively disabled.
Because this is PAPER-only and the risk layer's `is_stale` veto path would
reject any signal fired on stale data anyway, the failure mode was safe.

#### Root cause

Alpaca's crypto `/v1beta3/crypto/usd/bars` endpoint caps each response at
~167 rows for `timeframe=1Hour` **regardless of the caller's `limit`**
empirically confirmed via 6 direct `ccxt.alpaca.fetch_ohlcv` probes. Freqtrade's
`ohlcv_require_since` code path in `exchange.py:2827` computes:

```
since_ms = now - (ohlcv_candle_limit * required_candle_call_count) ms
```

with `ohlcv_candle_limit` defaulting to **500**, so the initial `since` landed
500h ≈ 20.8 days back. Alpaca then returned a page starting from that deep
window and truncated at ~167 rows — meaning the response covered
`[since, since+167h]` = `[NOW-21d, NOW-14d]`, ending **~1 week short of NOW**.
The cache was populated with bars ending 2026-09-29; every subsequent refresh
repeat-landed on the same stale page because the `since` never advanced.

Empirical probe matrix (30-day-ago initial `since`, various timeframes):

| since  | tf=1h rows | last bar returned | fresh? |
|--------|-----------|-------------------|--------|
| 3d back  | 72  | CURRENT | yes |
| 6d back  | 144 | CURRENT | yes |
| 7d back  | 167 | NOW−1h  | yes |
| 8d back  | 167 | NOW−25h | **no** |
| 10d back | 167 | NOW−3d  | no |
| 30d back | 184 | NOW−22d | no |

Anything requiring >7 days of 1h history in a single request returns a
truncated page that ends before NOW. `tf=1d` and `tf=5m` are unaffected
because their row-to-time ratio fits within one 167-row page for any
reasonable `startup_candle_count`.

#### Fix

Two coordinated edits, both inside PAPER configs only (no Freqtrade fork):

1. **`app/configs/config.alpaca.paper.swing.json`** — added
   `_ft_has_params.ohlcv_candle_limit_per_timeframe: { "1h": 144 }`. This
   shrinks the initial `since_ms` to `144h × 2 calls = 288h ≈ 12d`, which
   — combined with Freqtrade's second-call cursor advance — lands the
   most recent bar at NOW. Confirmed loaded at boot via the `_ft_has` log
   line: `'ohlcv_candle_limit_per_timeframe': {'1h': 144}`.

2. **`app/user_data/strategies/SwingAlt.py`** — reduced
   `startup_candle_count: 400 → 144`. The family warm-up (BB-20 + squeeze
   quantile 100 + EMA55 + ADX-14 + vol-20) needs ~120 bars max, so 144 gives
   comfortable headroom while staying inside the page-cap envelope. Without
   this second edit the strategy would have complained about insufficient
   history even after the fetch started returning fresh bars.

3. **`app/tests/test_dispatcher.py`** — three regression tests lock the
   invariant in:
   - `test_swing_alt_startup_candle_fits_alpaca_1h_page_cap` asserts
     `SwingAlt.startup_candle_count <= 144`.
   - `test_swing_alt_startup_candle_covers_family_warmup` asserts it's
     also `>= 120` so we cannot under-warm.
   - `test_fast_alt_startup_candle_fits_alpaca_5m_page_cap` guards the
     sibling `MomentumAlt` on its 500-row 5m budget.

#### Verification

Supervisor restarted with `--only swing` at 15:08:20Z. Freqtrade boot log
confirmed both fixes loaded (`Strategy using startup_candle_count: 144`,
`ohlcv_candle_limit_per_timeframe: {'1h': 144}`). **Zero** `Outdated history`
warnings in the 7-minute observation window across all three swing pairs
(compared to 30 warnings in the 3-minute pre-fix window). Bot heartbeated
normally and remained `state='RUNNING'`. Full test suite: **187 passed**.

### 11.2 Honesty about scope of "learning" in earlier docs

[`README.md`](../README.md) and the top-level `Multi-asset / multi-strategy /

as *self-learning*. That word is a stretch and the top-level README now
carries an explicit "**What this system is *not***" panel clarifying:

* **No ML.** Every signal family is hand-coded causal TA math (`families.py`).
  Grep across `app/risk / app/learn / app/user_data/strategies / app/indicators`
  for `torch / sklearn / tensorflow / statsmodels / hmmlearn / transformers /
  catboost / xgboost / lightgbm / freqtrade.freqai` returns zero matches.
  HMM was researched and deferred (`docs/Phase8_HMM_Report.md`), never wired.
* **No training.** `families.py` parameters (EMA65/STD65, RSI-14, BB-20/2,
  ADX-14, squeeze-quantile-100) are hardcoded and were not tuned by any
  automated loop during the expansion. No hyperopt, no gradient descent,
  no auto-rebalance.
* **No backtest-to-live feedback.** `docs/Backtest_Results_2026-10-22.{csv,md}`
  are static one-shot files written during Phase C. The learner reads the live
  Freqtrade `paper_trades` tables only. Backtest → registry retag is a
  human-mediated step.
* **No continuous market discovery.** `app/scripts/discover_assets.py` runs
  once, by hand, when the operator wants to expand the whitelist. Each
  executor's config uses `StaticPairList`. Nothing scans exchanges on a timer.
* **No dashboard.** `docs/Design.md` is UI spec only; the Streamlit Regime
  Trader app is not implemented. Telegram is currently the sole ops surface
  (plus Freqtrade's own Telegram RPC commands).

What Phase D actually implements is best described as **"expectancy-gated
auto-demotion"**: a closed-trade journal + a per-`(pair, family)` R-multiple
map + a one-way demotion gate that un-tradeable's any family whose average
R has dropped to ≤ 0 after n ≥ 20 samples. The gate can never
auto-promote; owner edits are required to reverse a demotion. On a young
account with 0 closed trades (the current state) the entire layer is
byte-for-byte inert and the sizing / gating behavior equals the pre-expansion
BTC baseline.

### 11.3 Second real defect found and fixed — supervisor orphan children on Windows

**Status: FIXED 2026-10-22.** Discovered while stopping the supervisor after the
live-run check; implemented and verified with a dedicated Windows process-lifecycle
test suite.

Symptom: running `Stop-Process -Force -Id <supervisor_pid>` on Windows kills
the supervisor but leaves its Freqtrade child executors, monitor, and learner
running as orphans. Reproduced twice:

- First live-run: supervisor PID `8352` killed, five orphans survived
  (`11344`, `24580`, `26260` monitor; `12912`, `21912` learner). Had to
  individually kill each.
- Second live-run (swing fix verification): supervisor PID `7424` killed, all
  children happened to inherit the kill this time (PowerShell `Get-Process |
  Where StartTime | Stop-Process -Force` explicit sweep), but the underlying
  defect is unchanged.

Root cause: `app/scripts/supervise.py` launches children with
`subprocess.Popen(..., creationflags=CREATE_NEW_PROCESS_GROUP)` on Windows so
that CTRL_C events sent to the supervisor's own console do not propagate to
children. That isolation is the correct design for signal routing, but the
corollary is that `TerminateProcess` on the parent does not automatically
terminate the process-group children — Windows does not enforce a job
object linking by default.

### Why signal/heartbeat handling alone was not enough

The pre-fix shutdown relied on the supervisor's `finally` drain (Ctrl+C →
`CTRL_BREAK_EVENT` to each child group). That path only runs on a *graceful*
exit; a `Stop-Process -Force` / Task-Manager kill / crashed host shell skips it
entirely, and `TerminateProcess` on the parent does not reach process-group
children. So the graceful path is a second layer, not the guarantee.

### Fix (implemented)

Primary containment is now an OS-level **Windows Job Object** configured with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, implemented with **stdlib `ctypes` only**
(no `pywin32`, no new dependency — Job Objects are not exposed by `psutil`):

* **`app/scripts/win_job.py`** (new): a `JobObject` wrapper (create → set
  kill-on-close limits → assign → close) plus a `ManagedProcess` handle and a
  `spawn()` that creates the child with `CREATE_SUSPENDED | CREATE_NEW_PROCESS_GROUP`,
  **assigns it to the job while suspended, then `ResumeThread`** — so a child can
  never spawn an escaping descendant in the pre-assignment window. `bInheritHandles`
  is `FALSE`, so the job handle is never handed to a child, and neither
  `CREATE_BREAKAWAY_FROM_JOB` nor breakaway limits are used, so descendants
  (including the `freqtrade.exe` that `run_paper.py` launches) inherit containment
  automatically. Any create/assign/resume failure raises `ContainmentError`
  and terminates the half-created process — **fail-closed**.
* **`app/scripts/supervise.py`**: creates one job at startup (`_init_job`); if
  containment cannot be established on Windows the supervisor **refuses to start
  (exit 4)** rather than launch unprotected workers. `spawn_managed()` routes
  every child through `win_job.spawn` on Windows (POSIX keeps the process-group
  fallback). `Managed.start()` catches `ContainmentError` and marks the spec
  `failed` (never retries, never launches uncontained). `Managed.stop()` is now
  idempotent and returns a status tag; `_drain()` performs graceful-then-forced
  shutdown, records a shutdown summary, then `TerminateJobObject` + `CloseHandle`
  as the backstop. A read-only startup scan (`_managed_cmdline_tokens`) reports
  any pre-existing UnboundBot workers (matched by specific script path in the
  command line, **never** by a bare `python.exe` name) and skips double-launching.

Graceful vs forced shutdown — operator notes:

* **Graceful**: Ctrl+C (or the SIGINT/SIGTERM handler) → `_STOP` set → `_drain()`
